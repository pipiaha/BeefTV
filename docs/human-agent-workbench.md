# 人机协作工作台约定

本文记录本 fork 的产品定位和工作方式，作为后续改造与业务交付的依据。文中的呈现要求是工作约定与产品目标，具体功能的实现和验收范围以代码及验证记录为准。

## 分工与交付关系

用户提出目标、约束和偏好，参与讨论、评审、选择和调整。负责当前业务的 Agent 理解和分析需求，准备材料资产，设计并推进业务流程，检查生成与制作结果，提出评审意见、组织返工，并面向用户交付。Agent 对工作过程、结果依据和未完成项作出清楚说明。

BeefTV 是双方共同对齐的工作台，承载业务流程编排、任务执行、项目状态、材料资产和交付结果。ComfyUI 及其他媒体工具承担其各自的生成和处理能力。Agent 可以通过外部 API、CLI、MCP 或已有界面操作推进工作；具体接入方式服务于同一份业务状态。

业务流程较长时，用户和 Agent 应能共同查看当前目标、正在做的事、所用材料、已有结果、评审意见和下一步。画布、项目和资产库承载这些可见信息，聊天用于提出需求、解释判断和协调决策。

## Agent 的工作方式

1. 明确业务目标、交付形式、约束和验收依据，将已确认内容记录在对应项目或画布中。授权范围和必要信息已经明确的工作持续推进；需要用户判断或超出授权的动作单独说明。
2. 准备并登记实际使用的材料，区分原始素材、生成素材、候选方案与最终版本。建立可追溯的引用，保留用户参与产生的决定。
3. 将业务步骤映射为可执行工作流，运行后把任务状态、产物和必要说明回填到同一项目。后台执行过程和用户看到的结果使用一致的对象与版本。
4. 检查产物是否符合业务目标。技术检查、内容质量、审美判断和用户意见分别给出依据；明确需要返工、尚未验证或等待用户判断的部分。
5. 交付可查看和可使用的结果，并指出其版本、来源、验收结论、限制与未完成项。关键成果同时留在工作台中，便于双方继续讨论、比较或修改。

## 工作台的呈现要求

业务步骤应使用用户能理解的名称和目的。工作流节点、模型名和底层参数作为执行细节，在需要检查或调整时可追溯。

对有实际意义的业务步骤，工作台应呈现：

- 目标、上下游关系和使用的材料；
- 当前状态与实际产物，必要的候选版本或对比；
- Agent 的检查结论、依据与建议；
- 用户反馈、已确认的决定和下一步动作。

信息优先放入现有项目、画布、资产或备注能力中；需要新增结构时再按实际使用缺口扩展。业务状态的写入遵循已有业务接口、归属校验和版本冲突处理。

## 验收与后续改造依据

技术任务完成、媒体可以解码和接口返回成功，分别证明对应的技术步骤。业务交付还需要对照需求检查内容，并把评审结论呈现给用户。“执行完成”和“验收通过”应有各自的依据。

评估新功能或参考项目时，重点检查它能否帮助双方理解业务、准备和复用资产、看清进展、比较方案、评审修改和追溯交付；同时检查 Agent 能否通过正式接口持续维护这些状态。

原生 ComfyUI 图像、音频、视频生成及组合导出已经完成首轮技术链路验证。该验证证明了执行能力；完整的业务过程呈现、评审记录和日常协作体验仍需按本约定逐步完善。内置聊天模型属于可选择的操作入口，外部 Agent 与用户共同使用工作台的流程也应完整成立。
